# Why

Concrete projects currently consume `Platform.*` packages through a mixture of
committed local feeds, machine paths, workspace inheritance and GitHub Packages.
Those projects can build on one desktop while failing in Docker, GitHub Actions
or a clean clone. GitHub Packages also requires a reader credential, while
nuget.org cannot safely host the existing generic IDs because `Platform.Core`
is already owned by another publisher.

# What Changes

- Publish the unchanged `Platform.*` package IDs as an anonymously readable,
  static NuGet v3 feed generated by Sleet and deployed through GitHub Pages.
- Replace the GitHub Packages release step with a Pages publication workflow
  that preserves previously published immutable versions.
- Define a portable consumer `NuGet.config`: the platform feed owns
  `Platform.*`; nuget.org owns all other packages.
- Add a user-level local-feed configurator. It uses `dotnet nuget add source`
  and adds the matching source map outside every consumer repository.
- Add an idempotent legacy-consumer migration/check command for repository
  feed configuration and the single overridable platform version property.
- Update adoption documentation and the installed adoption skill so agents use
  local sources only through user-level NuGet configuration.

# BFS Impact Map

| Surface | Impact |
|---|---|
| Package identity | `Platform.*` IDs, assemblies and C# namespaces remain unchanged |
| Release | Manual SemVer workflow packs, validates, updates a persistent static feed and deploys Pages |
| Credentials | No consumer credential; workflow uses only repository-scoped Pages/contents authority |
| New consumers | Canonical portable config and central version property become the generation contract |
| Legacy consumers | Preview/check/apply migration, no sibling checkout and no committed local path |
| Local development | User-level `platform-local` source plus unique prerelease versions |
| Supply chain | Package Source Mapping prevents `Platform.Core` substitution from nuget.org |
| Verification | Local feed generation, migration fixtures and cold consumer restore/build tests |

# Capabilities

- `platform-package-distribution`
- `platform-consumer-adoption`

# Non-goals

- Publishing or deploying a real remote feed from this local change.
- Renaming package IDs, projects, assemblies or C# namespaces.
- Making Forge a build-time or restore-time dependency.
- Committing local package paths, package binaries or credentials to consumers.
- Automatically choosing a local package with the same ID and version as a
  released package.
