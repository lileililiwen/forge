# Proposal: forge-web-gate-controls

## Why

The workbench Health card today renders a single doctor row — `gate-evidence` — that doctor already captured from the persisted evidence file (`src/doctor/probes.rs:379-454`). A sibling operator who wants to read the current cached gate status, or to ask Forge to re-run the gate and journal a fresh evidence record, has no way to do that from the browser. They have to drop to a terminal and run `forge gate status [TARGET]` (read) or `forge gate [TARGET]` (run) (`src/cli/functions_13.rs:235-379`); both reuse the same `forge::gate::run_gate` path (`src/gate/engine.rs:249`) the runtime boundary is built on.

That is the same CLI/portal gap a sibling operator can close in one click. The portal already carries the same Forge-wide admin session every other admin route uses (`src/api/admin/gateway.rs`), and the doctor `gate-evidence` finding is already proven to surface honest gate state from the persisted evidence file. What is missing is a *trigger*: a button that asks the server to re-run the gate and journal a fresh evidence record, and a status read that reuses the same envelope the CLI prints.

The contract hazard is the same one the CLI already handles: the gate runtime is external (Driftwatchdog / `driftwatch`), and Forge must not claim a state the runtime did not report. The model layer is explicit (`src/gate/model.rs:184` "Unknown or unexpected state strings become `unresolved` — never `pass`"; `src/gate/transitions.rs:509` "A state the runtime did not report is never synthesized"). A web layer that fabricates `pass` from a missing response — or that calls anything but `forge::gate::run_gate` to re-run — would break the invariant the whole plane rests on. This change keeps the browser as a thin caller of the same Core path the CLI uses.

## What Changes

- **One session-gated admin GET + one session-gated admin POST that wrap the existing `forge::gate` Core** — never the CLI, never a sibling subprocess. No new dependency, no schema change, no `forge::gate` API change.
  - `GET /v1/admin/projects/{id}/gate/status` — read-only. Resolves the managed project's directory server-side (`src/api/workbench.rs:156-170` `resolve` invariant: validated id, server-side `registry.inspect`, the browser never sends a path), then returns the same envelope the CLI prints for `forge gate status` (see `cmd_gate_status` at `src/cli/functions_13.rs:381-438`): a `gate` object carrying the persisted `GateEvidence` record with `freshness` overlaid, or an absent envelope with `aggregate: "unverified"` and the same human-detail note. The envelope is the parsed `GateEvidence` JSON (already versioned via `GATE_CONTRACT_VERSION`); nothing is fabricated. No path is included; the doctor's redaction posture is reused.
  - `POST /v1/admin/projects/{id}/gate/run` — explicit re-run. Resolves the same way, calls `forge::gate::run_gate` with the default `GateConfig::from_env()` (so `FORGE_GATE_BIN` is honoured and the same bounded argument-array invocation the CLI uses), then maps the returned `GateOutcome` to the wire envelope:
    - `GateOutcome::Evidence(ev)` → persists via the existing `forge::gate::save_evidence` (atomic tmp+rename; never a dry-run), journals a row via the same `registry.record_operation("gate", ...)` call the CLI uses (`src/cli/functions_13.rs:669-675`), and returns the parsed `GateEvidence` with `freshness` overlaid. The aggregate and per-check states are taken from what the runtime actually said; the record's `aggregate` field is whatever `classify_aggregate` produced, and the per-check states are whatever `GateCheckState::from_raw` mapped.
    - `GateOutcome::Rehearsal {..}` → **forbidden** on a real run. A document that declares itself a rehearsal is a rehearsal, and a rehearsal answers nothing (`src/gate/engine.rs:300-318`); the handler returns a typed `409 gate-rehearsal-not-evidence` so the browser can show "the runtime answered a rehearsal, not a verdict" and the cached evidence is left untouched.
    - `GateOutcome::Unavailable { reason }` → typed `502 gate-runtime-unavailable` with the bounded reason. Prior evidence is left byte-identical (`src/gate/engine.rs:33-36`); the browser renders the same `unavailable` finding the doctor renders for the same condition.
    - `GateOutcome::PlanPreview {..}` → only possible from a `--dry-run`; the browser never asks for a dry-run, so this variant is treated the same as `Unavailable` (typed refusal, no claim of pass, no journal row, prior evidence untouched).
  - The handler lives beside the rest of the beside-the-table admin routes in a new `src/api/admin/gate.rs` (`router.rs` is at 1000/1000, so the matcher and handlers live beside the table; see `src/api/admin/agent_identity.rs:32-63` for the precedent). Two new `Route` variants: `Route::AdminProjectGateStatus { id }` and `Route::AdminProjectGateRun { id }`. Registration in `src/api/router.rs` adds at most three new lines (one match arm for the path, two arms in the three `Route::AdminProject*` table sections — the project admin dispatch table, the admin-handler pre-table arm, and the project-admin bearer-handler arm).
- **Frontend workbench Health card** (`frontend/index.html:338-341`, `frontend/app.js:2151-2234`): the existing card grows two new sub-rows for the gate plane, both reusing the same `wb-health` box so no new card is introduced:
  - A **Gate status** sub-row that reads the parsed envelope's `aggregate`, `freshness`, and the short revision (`src/gate/engine.rs:178-182` `short_revision`). The label set mirrors the doctor's `gate-evidence` finding exactly so the two surfaces never disagree: `Passed`, `Blocked`, `Failed`, `Unknown`, `Stale`, `Absent`, `Unverified`, `Not applicable`. The run is `loadGateStatus(workbench.id)` from the existing detail-load path; it never blocks, never sets a spinner, and the workbench keeps its cached health as the source of truth until the operator acts.
  - A **Re-run gate** button that posts to the new `/gate/run` route. The button is disabled while the request is in flight (`Re-running gate…`), re-renders the same `Gate status` sub-row from the response, and on a typed refusal (runtime unavailable, blocked-but-rendered, rehearsal refusal) shows the existing `showWorkbenchNotice` with the same message envelope the typed error returns — the same `role=status` pattern `refreshHealth` already uses. No new dependency, no `innerHTML`, no inline script, no shell, no path interpolation in the JS.
- **No new CLI verb, no new `forge::gate` API**, no new external adapter contact. The browser is a thin caller of the same Core path the CLI uses; the runtime is unchanged.
- **Spec delta in `gate-runtime-evidence`** (the canonical spec). A new
  "Web surface for the gate status" requirement is ADDED — it captures
  the workbench sub-row contract and the never-fabricate-`pass` rule
  the wire must enforce. The existing `gate-runtime-evidence`
  requirements ("Declared gate runtime execution", "Revision-bound
  evidence lifecycle", "Honest surface projection", "Plan rehearsal
  document consumption") are unchanged: the new requirement cites them
  as the persistence / freshness / rehearsal-refusal / aggregate
  contract the web surface re-uses without restating. `doctor-maturity-
  assessment` is unchanged: the workbench card still calls the
  doctor's `gate-evidence` finding as the source of truth for the
  fast-read path; the new admin route is the explicit re-run trigger.

## BFS Impact Map

- **Requirements/scenarios:** `gate-runtime-evidence` ("Plan rehearsal document consumption" + "Revision-bound evidence lifecycle" — re-uses; no delta); `doctor-maturity-assessment` (the workbench already calls the doctor, the workbench card is the consumer of the doctor's `gate-evidence` finding — re-uses; no delta). `control-plane-portal` (workbench UI) — the new sub-row adds an additive UI surface, the existing `wb-health` box is the consumer.
- **Concepts/modules:** `forge::gate` (unchanged — the new handler delegates to `run_gate` and `save_evidence`, the existing public API); new `src/api/admin/gate.rs` handler + matcher; two new `Route` variants; one new constant in `src/api/admin/routes.rs` (if a route constant is required — the precedent `ROUTE_PROJECT_HEALTH_REFRESH` in `src/api/workbench.rs:54` keeps a route string per new admin POST/GET, and a parallel `ROUTE_PROJECT_GATE_STATUS` / `ROUTE_PROJECT_GATE_RUN` is added); one new entry in `IMPLEMENTED_WEB_ROUTES` (`src/api/command_catalog/routes.rs`) so the catalog can advertise the new verbs (the existing `gate` row is the catalog entry — its availability moves from `web_at` shape to two `web_at` rows, or the existing row is kept `web_at` for the run and a new `gate.status` row is added; decided in design); one new `Route` arm in the project-admin match block (`src/api/router.rs:313-317` area); two new arms in the two `Route::AdminProject*` tables (the pre-table admin arm at `:581` and the bearer-handler arm at `:770`, `:927`); two new `Route::AdminProjectGate*` registration in `src/api/model.rs:384` area; topbar no change; workbench sub-row in `frontend/index.html` and `frontend/app.js`.
- **Contracts:** `ROUTE_PROJECT_GATE_STATUS` = `GET /v1/admin/projects/{id}/gate/status`; `ROUTE_PROJECT_GATE_RUN` = `POST /v1/admin/projects/{id}/gate/run`; both 200/typed-failure envelopes; success body reuses the existing `gate-runtime-evidence` contract version string (`GATE_CONTRACT_VERSION`); no new `API_CONTRACT_VERSION`; absent evidence returns `200` with `aggregate: "unverified"` and a `freshness: "absent"` field (matches `cmd_gate_status` exactly at `src/cli/functions_13.rs:384-399`).
- **Callers/persistence:** no Core / CLI / registry-schema change. The handler opens the same registry `gate::run_gate` already opens, reuses `gate::save_evidence` (atomic tmp+rename), and journals through the same `registry.record_operation("gate", id, verdict, ...)` call the CLI uses. The new admin route is the only new caller.
- **Integrations:** no provider, no adapter subprocess on the read path; the run path spawns the same gate binary the CLI spawns, with the same argument array (`gate --format json`), the same `FORGE_GATE_BIN` override, the same bounded `GateConfig`, the same redaction (`capture_note`) and the same `MAX_GATE_OUTPUT_BYTES` cap. No new network on any path.
- **Tests/compatibility:** new contract binary `tests/web_gate_controls_contract.rs`. Static-token contract over the shipped `frontend/` assets — the new sub-row is in `index.html`, the click handler is wired in `app.js`, no `innerHTML` / `eval(` / `Function(` in the new block, no POST other than the named route. In-process admin route contract through `forge::api::handle` — anonymous → `401`, cross-origin → `403`, form-encoded body → `415` (POST only), success path renders the same aggregate/freshness the doctor reading would render, mutation test refuses to fabricate `pass` from a missing runtime answer. **The 401/403/415 boundary tests are not duplicated** if the existing `tests/web_assurance_browser_contract.rs` and `tests/web_shipping_provider_reads_contract.rs` already cover that boundary for the same path pattern (they do for `/v1/admin/projects/{id}/…` — `web_shipping_provider_reads_contract.rs:218-237` walks the anonymous-401 pattern across five `publish/providers|plugins|matrix` paths); the new test asserts the gate-specific failure-mapping only (absent evidence is `200 unverified`, blocked is `200 blocked`, unavailable is `502 gate-runtime-unavailable`, rehearsal-answered-real-run is `409 gate-rehearsal-not-evidence`) and links to the precedent in the design.
- **Concerns:** security (admin session cookie gate before any Core call — `guarded(db_path, request, ...)` envelope; CORS-exact origin; the run path inherits the CLI's argument-array invocation posture, no shell, no path interpolation; the journal row passes only `aggregate.label()` and the bounded `evidence_summary`, never a raw check note that might carry a project path); quality (no placeholder, no new dep, no `innerHTML`, source-file-size caps); a11y (the new sub-row reuses the existing `wb-health` styling, the button reuses the existing `button-quiet` + `aria-busy` pattern, the status text is rendered into the same `role=status` region the existing card uses); the never-`pass` invariant is preserved literally: the run handler never sets a `GateAggregate::Passed` value, and a missing response is rendered as the same `unavailable` finding doctor already renders.

## Capabilities

- A Forge operator with a valid `forge_admin_session` can read the current cached gate status for any managed project from the workbench Health card, with the same aggregate + freshness + short-revision triple the CLI's `forge gate status` prints.
- A Forge operator with a valid `forge_admin_session` can ask Forge to re-run the gate runtime for any managed project from the workbench Health card. The re-run uses the same `forge::gate::run_gate` path the CLI uses, persists the new evidence atomically, journals the verdict through the same `registry.record_operation("gate", ...)` call, and renders the result into the same sub-row. A runtime that is unresolvable, times out, or returns an unparseable document renders the same `unavailable` finding the doctor already renders — never a fabricated `pass`.

## Non-goals

- Surfacing the rehearsal document (`forge gate --dry-run`) to the browser: a rehearsal is never evidence (`src/gate/engine.rs:300-318`) and exposing it as a "result" would re-introduce the "rehearsal answered a real run" footgun the model is built to prevent. The new run route is `dry_run: false` only; a sibling operator who wants a rehearsal uses the CLI.
- Surfacing release-evidence consumption (`forge gate evidence`) to the browser: that is a sibling export verb (`gate-evidence-export-consumption`) with its own `consume_export` path, not the gate runtime path; the workbench card calls the gate runtime path only.
- Re-issuing the docstring-correct "never a pass" comment as a new invariant: the invariant already exists at `src/gate/model.rs:184` and `src/gate/transitions.rs:509`; the new handler enforces it by delegating to `run_gate`, not by re-asserting it. A duplicate copy would be a second place to drift.
- A "remove gate evidence" UI: not in the audit gap, and not part of the operator's gate run loop.
- A bulk re-run of the gate across the whole fleet: the route is project-scoped (one managed id), and the workbench card sits in the single-project workbench — fleet operations are the catalog's "gate (fleet)" row, which is its own surface.
- Showing the gate's stdout/stderr in the browser: the CLI redaction posture (`capture_note`, `bound_note`) is preserved on the wire, but the browser never asks for raw output; the existing `evidence_summary` and `aggregate.label()` carry everything the operator needs.
- Publishing or pushing anything: the change is read-only on the registry/journal and writes only to the project's own `.forge/gate/{id}/evidence.json` (atomic tmp+rename), the same single file `save_evidence` always writes.
